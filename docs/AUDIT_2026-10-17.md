# LogAsis AI Analyst — Engineering Audit (Phase 1)

Date: 2026-10-17
Scope: full trace of UPLOAD → PARSE → NORMALIZE → INDEX → QUESTION → ANSWER, plus the
synthetic benchmark corpus at `E:\LogAsis_AI_Analyst_Benchmark` (all 7 file SHA-256 hashes
verified against `manifest.json` — all match).

Every defect below was reproduced by execution before being listed. Reproduction scripts
were run against the real ingestion pipeline (`parsers.json_log` → `core.analytics` →
`core.log_dataset` → `core.query_engine`).

## Confirmed root causes (reproduced)

### C1. `EventIndex.intersect` returns ALL rows when every position set is empty
- File: `core/event_index.py:381-390` (via `LogDataset.filter_and`, `core/log_dataset.py:138-140`)
- Reproduced: `filter_and(("source_ip","203.0.999.999"), ("action","failed_login"))`
  on `authentication_large.jsonl` (2,500 events) returned **854 rows instead of 0**.
- Impact: any conjunctive filter with one non-matching condition counts the whole
  matching set of the *other* conditions. A direct source of wrong counts and
  wrong "all events" claims.
- Fix: intersect fails closed (empty intersection ⇒ zero rows); empty condition list
  returns all rows only when *no conditions were supplied at all*.

### C2. `QueryEngine._finalize` corrupts counts when a result limit is applied
- File: `core/query_engine.py:390-395`
- Reproduced: AND(source_ip=198.51.100.23, action=failed_login) with `limit=5`
  reported `count=5`; the true match count is **45**.
- Impact: any limited plan reports the truncated length as the count → the model and
  the UI believe the sample is the total. This is the "incorrect exact counts" defect.
- Fix: `count` always reports the complete matching set; `returned_count` reports the
  bounded sample; `truncated`/`exhaustive` flags added.

### C3. `events_to_dataframe` crashes on malformed/mixed timestamps
- File: `core/analytics.py:29-49`
- Reproduced: `parser_edge_cases.jsonl` (timestamp `not-a-timestamp`) raises
  `AttributeError: Can only use .dt accessor with datetimelike values` — the file cannot
  be loaded at all through the normal upload path.
- Also: mixed naive/aware timestamps produce an object-dtype column with the same crash.
- Fix: normalize parsed timestamps to a single UTC dtype; repair path coerced to the
  same dtype; per-row parse failures keep the event (with `timestamp_parse_failed`
  flag) instead of rejecting the file. NaT `hour`/`date` are empty strings.

### C4. Exact-count questions are answered by LLM estimation over a bounded sample
- Files: `ai/agent.py:336-435`, `ai/investigation_agent.py`
- The investigation runtime has **no deterministic aggregation/count tool**. Search
  tools return ≤12 records; the model sees ≤64 evidence records and estimates totals
  from them. For "How many failed SSH authentication attempts came from 198.51.100.23?"
  (45 matching events in 2,500) the model can only guess.
- Fix: deterministic question understanding + validated query plans + indexed
  execution (`core/question_understanding.py`, `core/deterministic_qa.py`), plus a
  `count_events` tool for the agent and deterministic facts injected into synthesis.

### C5. Set-level count validation rejects true counts (false rejections)
- File: `ai/claim_grounding.py:523-604` (`_aggregate_support_gap`)
- Reproduced by inspection + execution: a correct claim "45 failed logins" is validated
  against only the ≤64-record evidence bundle; when the bundle holds fewer than 45
  matching records the claim is rejected as "aggregate count is not supported".
- Fix: grounding context now carries deterministic query results
  (`deterministic_counts`); count claims are verified against full-dataset results,
  and only *contradicted* counts are rejected.

### C6. GUI freezes ("Not responding") during log upload
- File: `gui/main_window.py:6231-6303` (`load_log_file`)
- The whole pipeline runs on the Qt GUI thread: file read → parse →
  `events_to_dataframe` → `LogDataset(...)` (index + analytics cache + manifest) →
  filter rebuild → table render. For large files Windows marks the window
  "Not responding". (Background `AnalysisWorker` starts only *after* this block.)
- Fix: new `IngestionWorker` (QThread) performs parse/index off the GUI thread with
  progress reporting; the GUI thread only renders results when the worker finishes.

### C7. `core/claim_verification.py` classifies nearly every claim as VERIFIED_FACT
- File: `core/claim_verification.py:66-80`
- Certainty language detection uses substring checks including `"is"`, `"was"`,
  `"were"` — "is" matches inside "analysis"/"this". Any claim with ≥2 events
  becomes HIGH-confidence VERIFIED_FACT regardless of evidence.
- Fix: classification now derives from actual record support (concrete attribute
  overlap, outcome evidence, contradiction checks) rather than confidence keywords.

### C8. EventIndex timestamp sorting crashes on mixed naive/aware timestamps
- File: `core/event_index.py:142` — `sorted()` over mixed naive/aware datetimes
  raises `TypeError`; `timestamp_range` comparisons likewise.
- Fix: `_parse_timestamp` normalizes to UTC-aware datetimes.

### C9. Query plans silently weakened during compilation
- File: `core/query_engine.py:99-181` — invalid sub-plans are dropped, so a malformed
  model-produced AND plan can degrade into "match everything".
- Fix: compile records validation errors; execution refuses (fails closed) plans with
  unknown fields or unsupported operators instead of silently widening the result.

## Benchmark corpus status
- 7/7 SHA-256 hashes match `manifest.json`.
- Ingestion through the real parser: 2,500/2,500 × 5 files, 2,494/2,494 linux_audit,
  5/5 parser edge cases (after fix C3).
- 18 ground-truth questions: 11 exact_count, 1 correlated_events, 5
  insufficient_evidence (abstention), 1 causality_not_established.
- Ground truth contains `filters`, `expected_count`, and `event_uid` evidence IDs;
  the evaluator maps runtime `EVID-NNN` (row position N-1) ↔ source `event_uid`.
- Leakage control: predictions are written separately from ground truth; the runner
  never passes `filters`/`expected_count`/`evidence_ids` into the prompt or corpus.

## Planned fix architecture (implemented in this change)
1. Deterministic factual layer: `core/question_understanding.py` +
   `core/deterministic_qa.py` — question → validated plan → indexed execution →
   exact answers with coverage accounting. No LLM arithmetic.
2. Investigation runtime: deterministic `count_events` tool, deterministic facts in
   synthesis prompts, coverage/completion status, bounded steps retained.
3. Claim grounding: deterministic count corroboration; causal/anti-hallucination
   guards for "prove X" questions; HYPOTHESIS claim class.
4. GUI: async ingestion worker (fixes "Not responding").
5. `training/` package: dataset validation, benchmark runner, evaluator,
   training-example export (split by scenario, leakage-safe).
6. `tests/` regression suite covering the reproduced defects and the benchmark.
